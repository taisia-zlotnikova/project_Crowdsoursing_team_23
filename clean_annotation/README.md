# Чистовая версия процесса разметки

Четыре последовательных ноутбука и самостоятельный API-код для разметки,
независимого REVIEW, переразметки и экспорта эталонного датасета.
Процесс не зависит от старых notebooks и scripts.

## Запуск

Из корня проекта:

```bash
python3.13 -m venv .venv
.venv/bin/python -m pip install -r clean_annotation/requirements.txt
.venv/bin/jupyter lab
```

1. **01_setup_and_settings.ipynb** — единая конфигурация, оценка бюджета, подключение текущих ресурсов либо создание самостоятельного закрытого набора, отдельная смена цены/перекрытия.
2. **02_launch_and_review.ipynb** — обучение и экзамены, запуск выбранного этапа, скачивание снимков, BBOX → REVIEW, оценка экзамена, выдача навыков, пилот и основной пул.
3. **03_rework_and_audit.ipynb** — свежие проверки, отбор BAD, исключение ручных OK, переразметка → повторный REVIEW, архив исходных ответов и расходов.
4. **04_final_dataset_and_deliverables.ipynb** — полностью локальное воспроизведение итогового датасета в JSONL/JSON/CSV/COCO/YOLO и HTML из опубликованных материалов.

По умолчанию `PROFILE='existing'`, `ENABLE_WRITES=False`. В существующем профиле используйте `attach_existing()` — он проверяет владельца проектов и создаёт только локальный реестр. Для нового запуска `PROFILE='new'`, уникальный namespace и актуальная дата expires_at. Создание вызывается отдельно от платной выдачи. Для изменений явно включите ENABLE_WRITES, а затем соответствующий переключатель одной ячейки. Не запускайте платные этапы через Run All.

Токен вводится скрыто через getpass либо задаётся в YANDEX_TASKS_TOKEN. Не вставляйте его текстом в ячейки, JSON или git. Закрытые исходные идентификаторы и сетевые журналы находятся в private/ (игнорируется git). Уже собранные псевдонимизированные материалы доступны в ../deliverables/annotation/; они не требуют токена.

## Настройки

В config.json: инструкции, стоимость страницы, число задач/страницу, overlap, сроки и пороги. Экзамены: одна страница с 10 примерами. Overlap экзамена = число полных попыток; увеличить с 20 до 40 можно через update_settings(...,overlap=40), повторный вызов оставляет 40. Участник с экзаменационным навыком повторно к экзамену не допускается; ограничение числа страниц также сохраняется. В BBOX доступ задаётся навыками bbox_exam_score≥90 и bbox_access=100. REVIEW: review_exam_score≥80 и review_control_score≥75 либо ещё не установлен. Обучение: 80%.

BBOX-пулы: отложенная приёмка 1 день. REVIEW в новом воспроизведении: немедленная приёмка, качество контролируется эталонами и навыками. Исторические настройки сохранены в evidence и могут отличаться — смена config не переписывает их сама. REVIEW-перекрытие 3, смешивание до 4 реальных проверок + 1 контроль. Не снижайте число контрольных до нуля. 25 фото пилота и 375 основных не пересекаются; 10 экзаменационных фото отдельные. В шаблонах сохранены текущие интерфейсы без сложного пользовательского JavaScript.

Новый namespace создаёт два проекта, четыре навыка, два обучения и восемь рабочих/экзаменационных пулов. Старая схема 100+100+100+75 не воспроизводится: main один, на 375 фото. Рамки в заданиях — normalized XYWH. В review_task ссылка хранится в image, геометрия в result, наличие бабочки в source_status. Review не перерисовывает боксы.

## Что выполняется автоматически

На платформе автоматически работает экзамен REVIEW с 10 известными ответами, назначение навыка и фильтр рабочих пулов. Запуск/модерация и передача BBOX → REVIEW — отдельные ячейки, постоянного демона нет. BBOX-экзамен оценивается по REVIEW или явному ручному решению; оплата сама по себе не означает допуск. Денежные ACCEPTED/REJECTED в этой чистовой версии автоматически не меняются.

Переразметка: BAD > OK среди независимых голосов с корректной связью с исходным заданием; ханипоты не учитываются. Используются исторические голоса, без ретроспективного удаления из-за упавшего навыка; порог платформы ограничивает будущую выдачу. Технические/неоднозначные ответы идут на ручной разбор. Статистика голосов сама по себе не даёт права считать непроверенное фото хорошим. Новая версия заменяет старую при отборе, пока её REVIEW не завершено, старый BAD не создаёт ещё один раунд. Уже завершённый повторный неудачный раунд требует отдельного решения, а не перезаписи тех же task ID.

manual_by_photo.json содержит исторические ручные исправления только этого датасета; для других фото его нужно заменить. Для повторной редакции инструкции меняйте HTML проекта осторожно: старые пулы могут сохранять версию интерфейса. Для изменения схемы создавайте новый namespace, а не перезаписывайте task_spec работающего проекта.

## Материалы и затраты

```bash
python3 clean_annotation/evidence.py
python3 clean_annotation/final_export.py
python3 -m unittest discover -s clean_annotation/tests -v
```

Архив ../deliverables/annotation_evidence.zip содержит исходные задачи, ответы и проверки с псевдонимами исполнителей, инструкции, ручные решения, настройки и ссылки. Координаты и содержание ответов сохранены; оригиналы с исходными ID остаются закрытыми в platform/private/. Комиссия 40% считается отдельно; pending — резерв, не расход. Используется reward конкретной выдачи, не текущая цена пула. Бонусы/возвраты/фактические списания нужно сверить с биллингом заказчика. Ошибки загрузки и неизвестные reward не заменяются нулями.

Воспроизводимый финал: 400 фото, 354 положительных, 46 отрицательных, 358 рамок. В архив разметки изображения не включены; URLs и лицензии в манифесте, HTML требует интернет. Есть 18 ручных подтверждений, три ручные перерисовки и один ручной отрицательный ответ. Никаких обучающих/экзаменационных задач и ханипотов в финальных 400 нет.
